- [x] Task 5.1 (2026-08-30): Messaging service — `ChatSession`/`Message`/`RatchetSessionState`/`TransportEndpointConfiguration` entities, `IMessagingService`/`MessagingService` (`src\SecureApp.Data\Messaging\`), repositories (`IChatSessionRepository`, `IMessageRepository`, `IRatchetSessionStateRepository`, `ITransportSettingsRepository`), schema V3 (`chat_sessions`, `ratchet_session_states`, `messages`, `transport_settings` — `SqlCipherConnectionFactory.CurrentSchemaVersion` 2→3). **Scope call: 1-on-1 (Direct) sessions only** — group E2EE needs a different protocol (Sender Keys/MLS, not plain Double Ratchet), deliberately left for a later milestone rather than silently doubling this pass's scope.
- [x] Task 5.2 (2026-08-30): `IRatchetService`/`RatchetService` — this repo's own adaptation of the Signal Double Ratchet, not a claim of spec compliance (see the class's own doc comment for the full reasoning): an ML-KEM-based X3DH-style handshake (`ICryptoService.EncapsulateAsync`/`DecapsulateAsync`, new methods) establishes a shared root key, from which two independently-keyed HKDF chains (`ICryptoService.DeriveKeyAsync`, new) give a real, correct **symmetric-key ratchet** — per-message forward secrecy, out-of-order/skipped-message-key support (bounded, `MAX_SKIP=1000`), fail-closed on tampered ciphertext **without desynchronizing the chain** (a real bug caught and fixed during implementation — the initial version persisted the advanced chain key before verifying decryption succeeded, which would have turned one corrupt message into a permanent DoS on the whole session). **Deliberately not implemented**: the asymmetric "DH ratchet" (post-compromise security via re-keying) — `RatchetSessionState.RatchetDh` exists on the entity as scaffolding for a future pass, but nothing calls it yet, since ML-KEM's encapsulation isn't symmetric like Diffie-Hellman and a correct bidirectional re-key protocol needs real design work out of scope here.
- [x] Task 5.3 (2026-08-30): Document attachment bridging — `Message.AttachmentDocumentId` references an already-imported `Document` (schema: `ON DELETE SET NULL`, mirroring `DocumentFolder`'s precedent — deleting a document must not delete chat history).
  - **Design note verified during implementation:** `Message.Payload` is **not** the wire-format ratchet ciphertext (that's one-shot and discarded after use — the whole point of forward secrecy, so it can never re-decrypt anything for redisplay). It's re-encrypted under a normal, vault-mediated `KeyPurpose.MessageStorage` key via the same `ICryptoService.EncryptAsync`/`DecryptAsync` path `Document.EncryptedContent` already uses — redecryptable on demand at any time. The Double Ratchet protects the message only in transit; SQLCipher protects it at rest, same as everything else in this app. `Message.Header` is kept separately as the actual wire-format header for a future transport's benefit.
  - **Local chat identity key:** a peer's device must already hold the *other* device's identity public key before a handshake can be initiated (ML-KEM encapsulation needs the recipient's public key up front) — so `IMessagingService.GetLocalIdentityPublicKeyAsync()` exposes one shared, long-lived `KeyPurpose.ChatIdentity` key per device (minted once, reused across every session — not a fresh key per session), meant to be exchanged out-of-band (e.g. a future QR-code flow). New `ICryptoService.GetEncryptionPublicKeyAsync` retrieves a previously generated key's public half back out of the vault (mirrors the signing-key path, which already stored `dsa-pub`; encryption keys didn't store `kem-pub` until now).

Crypto design, named directly rather than left implicit: deliberately does **not** build a new group ratchet (Sender Keys/MLS), despite `ChatSession`'s own pre-existing remark flagging that as the assumed direction. Trade-off stated explicitly: O(n) work per message and O(n²) total sessions across a group instead of Sender Keys' O(1)/O(n) — entirely reasonable for a small, admin-curated team (the actual user), and it reuses 100% already-tested crypto rather than a hand-rolled ratchet, which is where real vulnerabilities tend to get introduced. A founder-mediated alternative (only the founder holds pairwise sessions, relaying everyone else's traffic) was considered and rejected: it would make ordinary group function depend on the founder's device being reachable, a materially worse resilience property.
    - **New Domain**: `GroupChat` (id minted once by the founder and shared verbatim across every member's own local copy — unlike `ChatSession.Id`, which is independently generated per side — so a received message's `GroupChatId` tag needs no per-recipient correlation step) and `GroupMember` (no cached `ChatSessionId`; the pairwise session to use is always resolved fresh via `FindExistingSessionAsync(PublicKey)`, so it can never go stale). `Message`/`MessageEnvelope` gained optional `GroupChatId`/`GroupMessageId` tags (a group message is still an ordinary pairwise-session row, just tagged — not a new message type) — `GroupMessageId` is shared across a sender's own N fan-out copies of one logical message so their own thread view can collapse them back into one bubble; a recipient only ever gets one copy regardless. `IGroupMemberRepository.ReplaceAllAsync` always takes a **full** membership snapshot, never an incremental diff — creating, renaming, adding, and removing a member are all "recompute the full list, persist it, re-broadcast it" the same way, which collapses what could have been four separate sync protocols into one.
    - **Bootstrapping a full mesh without races**: when a device processes a group-invite snapshot naming members it isn't yet paired with, both it and the other member would otherwise independently try to initiate a pairwise handshake with each other simultaneously — which deadlocks both sessions in `PendingHandshake` (each side waiting for the other to accept an invite it never looked for, since `FindExistingSessionAsync` finds its own self-initiated session first and treats the peer's incoming invite as "already paired, nothing to do"). Fixed with a deterministic tie-break (`App.xaml.cs.ShouldInitiateTo`): compare the two devices' chat-identity public keys byte-for-byte, only the one that sorts "greater" initiates — the other waits, and the already-existing `OnPairingInviteReceived` auto-accepts whenever that arrives. The founder itself never needs this tie-break when first creating a group (nobody else has the group id yet to race against) — it only matters for member-to-member pairing discovered independently on both their own devices once the snapshot reaches them.
    - **Relay**: new `"group-invite"`/`"group-invite-deliver"` frame, an exact mirror of the existing `"pairing"`/`"pairing-deliver"` (same live-or-outbox routing, same opaque-blob-the-relay-never-parses reasoning) — duplicated rather than generalized, consistent with how `"pairing"` itself was added alongside `"send"`.
